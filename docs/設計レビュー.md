# Phase 0 設計レビュー結果

作成日: 2026-11-22。数値と挙動はすべてこの日に手元で実測したもの。推定を含む箇所には「推定」と明記する。

## 0. 要約

- 3 層設計（ITF デコーダ / ステップ抽出・再生・比較 / アダプタ）で足りる。ただし、公式 quint-connect が暗黙に担っている責務のうち 9 点を、明示的な仕様として中核に入れる必要がある（§5）
- 当初の未確認事項「Rust バックエンドで `mbt::actionTaken` がどう記録されるか」は解消した。名前付きアクションなら Rust・TypeScript の両バックエンドで正しく記録される。空文字になるのは `any` の枝が無名の式のときだけで、これは両バックエンドで同じ（§2.4）
- 想定外の事実が 2 件見つかった。別件として報告する（§9）
  - Rust バックエンドでは、16 桁以上の整数が bignumber.js の内部表現 `{"s","e","c"}` のまま ITF に書き出される
  - Rust バックエンドの `vars` 配列に mbt 変数が重複して入る
- 判断が要る事項が 4 件ある（§6）。うち D1（差分テストの手段）と D2（在庫予約モデルの観測可能性）は、Phase 2・3 の終了条件に届くかどうかを左右する

## 2. 確認できた事実

検証用の仕様は `phase0/spec/` にある。golden は `phase0/gen-golden.sh` で `itf/testdata/golden/` に 15 ファイル生成した。

### 2.1 トップレベルと `#meta`

- トップレベルのキーは `#meta`・`vars`・`states` の 3 つ。`params` と `loop` は出ない
- トレースの `#meta` は `format`・`format-description`・`source`・`status`・`description`・`timestamp` を持つ。`description` には生成時刻（ローカル時刻の文字列）が、`timestamp` にはエポックミリ秒が入るため、実行ごとに値が変わる
- 各状態の `#meta` は `{"index": n}` だけを持つ
- seed は ITF に記録されない。再現に必要な生成条件は ITF の外で残す必要がある

### 2.2 値の表現

| Quint の型 | ITF 上の表現（実測） | 備考 |
|---|---|---|
| `int` | `{"#bigint": "<10進文字列>"}` | 小さな値も常にこの形で、素の JSON 数値は出なかった。負数は `"-5"`。ADR-015 は素の数値も許すため、デコーダは両方を受ける |
| `bool` | JSON の真偽値 | |
| `str` | JSON 文字列 | |
| `List[a]` | JSON 配列 | 順序に意味がある |
| タプル | `{"#tup": [...]}` | unit は `{"#tup": []}` |
| `Set[a]` | `{"#set": [...]}` | 要素の並び順はバックエンドで異なる（下記） |
| `a -> b` | `{"#map": [[k, v], ...]}` | キーは任意の値（int、タプルなど）。並び順はバックエンドで異なる |
| レコード | JSON オブジェクト | キーはアルファベット順で出る |
| 直和型 | `{"tag": "<名前>", "value": <値>}` | 値のない variant の value は `{"#tup": []}`。Option も同じ形（`Some` / `None`） |

`#set` と `#map` の並び順は、同じ値でもバックエンドによって変わる。

- Rust: 値の順。`(1,"x"), (2,"y"), (20,"p")`
- TypeScript: 文字列順に近い並び。`(1,"x"), (10,"q"), (2,"y")`

したがって順序に依存した比較はできない。

### 2.3 Rust バックエンドの整数表現の欠陥

| 値 | Rust バックエンドの出力 |
|---|---|
| `10^15 - 1`（15 桁） | `{"#bigint": "999999999999999"}`（正常） |
| `10^15`（16 桁） | `{"s": {"#bigint": "1"}, "e": {"#bigint": "15"}, "c": [{"#bigint": "10"}]}` |
| `-(10^15)` | `{"s": {"#bigint": "-1"}, "e": {"#bigint": "15"}, "c": [{"#bigint": "10"}]}` |
| `2^53 - 1` | `{"s": ..., "e": {"#bigint": "15"}, "c": [{"#bigint": "90"}, {"#bigint": "7199254740991"}]}` |
| `2^62` | `{"s": ..., "e": {"#bigint": "18"}, "c": [{"#bigint": "46116"}, {"#bigint": "86018427387904"}]}` |
| `2^70` | 生成時点で `QNT601 Integer overflow` となり停止する（evaluator は 64 bit 整数） |

- 境界は「10 進 16 桁以上」。2^53 ではない
- TypeScript バックエンドは `2^70` も `{"#bigint": "1180591620717411303424"}` と正しく出す
- 原因（推定）: Quint の TS 側は、Rust evaluator の出力を `parseJsonBig`（json-bigint）で読む。同関数のコメントには「15 桁を超える整数は bignumber.js の値になる」とある。その BigNumber オブジェクトが整数として扱われず、レコードとして ITF に書かれていると考えられる。コメントと出力形の一致までは確認したが、変換箇所そのものは特定していない
- この形は、フィールド `s`・`e`・`c` を持つ正当なレコードと見分けられない。そのため、ドライバ側で知らせずに復元すると誤りを持ち込む（§6 D3）

### 2.4 `mbt::actionTaken` の記録規則

次の表は実測の結果で、Rust と TypeScript で同じだった。

| 仕様の形 | 記録された名前 |
|---|---|
| 初期状態 | `init` |
| `step = any { outerBump, ... }`、`outerBump` の中で `innerBump(d)` を呼ぶ | `outerBump`（内側の `innerBump` ではない） |
| `step = any { group, idle }`、`group = any { left, right }` | `right`（外側の `group` ではない） |
| `step = bump`（`any` なし） | `step`（`bump` ではない） |
| `any` の枝が無名の式（`all { ... }` や `x' = x + 10` の直書き） | `""`（空文字） |

Rust evaluator v0.7.1 のソース（`evaluator/src/storage.rs` と `builtins.rs`）で仕組みも確認した。

- アクション定義に入るたびに `track_action` が呼ばれ、まだ名前が記録されていなければその名前を記録する
- `actionAny` は枝を試すたびに `clear_metadata` でアクション名と nondet の記録を消す

つまり記録されるのは「最後に選ばれた `any` の枝の中で、最初に入った名前付きアクション」である。

ドライバへの影響は次のとおり。

- アダプタの対応表のキーは、Quint 側の上記規則で決まる名前になる。入れ子の `any` では内側の枝の名前になる
- 空文字は「無名アクション」としてエラーにする（quint-connect と同じ扱い）
- TypeScript バックエンドで actionTaken が空になるという報告は、0.33.1 では名前付きアクションについて再現しなかった。空になるのは無名の枝だけ

### 2.5 `mbt::nondetPicks`

- 仕様中のすべての nondet 名をキーに持つレコードで、全状態に同じキー集合が出る。nondet がない仕様では `{}`
- 各値は Option 型の variant。そのステップで使われた nondet だけが `{"tag": "Some", "value": v}` になり、それ以外は `{"tag": "None", "value": {"#tup": []}}` になる
- 別のアクションで同じ名前の nondet を使うと、1 つのキーにまとめられる（probe の `outerBump` と `paint` がどちらも `d` を使う例で確認）
- init 内の nondet は状態 0 で `Some` になる
- `any` の外側で宣言した nondet（counter の `k`・`who`）も、選ばれた枝（`reset`）が使わなければ `None` で記録された。nondet を記録する時機の詳細は追っていない。アダプタは「使う枝では `Some` になる」ことだけを前提にする

### 2.6 状態変数の並びと `vars`

- Rust バックエンドの `vars` は名前順で、`mbt::actionTaken` と `mbt::nondetPicks` が 2 回ずつ入る
- TypeScript バックエンドの `vars` は宣言順で、重複はない
- `--mbt` を付けなければ mbt 変数は出ない
- 各状態のオブジェクトのキーは、どちらのバックエンドでも名前順

ドライバは `vars` に頼らず、各状態のキーから変数を得る。

### 2.7 生成の再現性

- tictactoe で同じ seed（`0x2a`、50 本）を 2 回生成したところ、`states` は全件一致した。`--n-threads=1` と既定の 10 でも一致した
- golden 15 ファイルを 2 回生成したところ、`states` は全件一致した
- 同じ seed でも Rust と TypeScript では別のトレースになる（乱数系列が異なる）

評価器の凍結は seed・本数・ステップ数の固定で再現できる。ただし Quint の版を変えるとトレースも変わるため、凍結の対象は生成済みファイルにし、生成条件は再生成の手順として残す。

## 3. 公式 quint-connect との突き合わせ

quint-connect v0.1.2 のソースを読んで責務を洗い出した。

| quint-connect の責務 | 実装の所在 | 3 層設計での扱い |
|---|---|---|
| トレース生成（`quint run --mbt` を一時ディレクトリへ実行） | `trace/generator` | 対象外（最小構成に含めない）。quint CLI は外から叩く |
| ITF のデコード | 外部 crate `itf` 0.4 | 層 1 で自作する |
| 状態 0 も 1 ステップとして扱い、`init` をアダプタに渡す | `runner::replay_traces` | 層 2。同じにする（差分テストでステップ番号を揃えるため） |
| 各ステップの直後に状態を比較する（状態 0 も含む） | `runner::check_state` | 層 2 |
| 空の actionTaken をエラーにする | `runner` | 層 2 |
| nondetPicks の Option を 1 段だけ外し、`None` を除く | `driver/nondet.rs`、`value/option.rs` | 層 2 |
| 比較対象の射影（State 型にあるフィールドだけを比べる） | serde の既定動作 | 層 2 で明示的に扱う（§5） |
| 状態の値の正規化 | serde による型付き復号（BTreeMap などへ） | 層 1・2 で正準形の比較として明示する（§4） |
| 不一致の表示（Debug 出力の行 diff） | `similar` crate | 層 2。値のパス単位で差分を出す |
| 対象の panic | Rust のテスト失敗として外に出る | 層 2 で recover し、ステップ単位の失敗として報告する |
| 未対応のアクション名をエラーにする | `switch!` マクロ | 層 3 の対応表の検索失敗として層 2 が報告する |
| sum-type 方式のステップ抽出、状態の入れ子パス指定 | `Config` | 対象外（最小構成に含めない） |
| ドライバの再利用 | 全トレースで 1 インスタンスを使い回し、`init` でリセット | 変える。トレースごとに新しいアダプタを生成する（トレース間の状態の漏れを構造的に防ぐ） |
| トレースの処理順 | `read_dir` の順（OS 依存） | 変える。ファイル名で整列する |
| 失敗時の挙動 | 最初の失敗で全体を打ち切る | 変える。トレース単位で判定し、各トレースは最初の不一致で止める |

不足だった責務は、表の「層 2」「変える」の行にある。いずれも「ITF をデコードして比較する」とだけ書くと抜け落ちる、暗黙の仕様である。

## 4. 比較時の正規化要件

| # | 対象 | 要件 | 根拠 |
|---|---|---|---|
| N1 | 整数 | `#bigint` 文字列と素の JSON 数値の両方を `math/big` で受ける。float64 を経由しない（`json.Decoder.UseNumber`）。小数・指数表記は拒否する | §2.2、ADR-015 |
| N2 | 集合 | 順序を無視し、正準形の値で整列して比べる。重複要素は 1 つにまとめる | §2.2（バックエンド間で順序が違う） |
| N3 | マップ | キーと値の組の集合として、正準形のキーで整列して比べる。キーの重複はデコードエラーにする。キーは任意の値を取る | §2.2 |
| N4 | レコード | フィールド順を無視する。レコードと文字列キーのマップは別物として扱う | §2.2 |
| N5 | タプル・リスト | 順序どおりに比べる。タプルとリストは別物として扱う | §2.2 |
| N6 | 直和型 | `tag`・`value` を持つレコードとしてそのまま比べる。専用の種別を設けなくても、両側が同じ規則で符号化すれば一致判定は成り立つ | §2.2 |
| N7 | `#unserializable` | 比較不能としてエラーにする（一致扱いにしない） | ADR-015 |
| N8 | mbt 変数 | `mbt::actionTaken`・`mbt::nondetPicks` は比較対象から外す | §2.5 |
| N9 | メタ情報 | `#meta`・`vars` は比較に使わない | §2.1、§2.6 |
| N10 | 実装側の空値 | Go の nil の map・slice と空の map・slice を同じ空集合・空リスト・空マップとして扱う | Go 固有 |
| N11 | 実装側の整数型 | int・int64・uint64・`*big.Int` などを同じ整数として扱う | Go 固有 |
| N12 | 射影 | アダプタが返した変数だけを比べる。仕様にない変数名をアダプタが返したらエラーにする（綴りの誤りで比較が黙って抜けるのを防ぐ）。比べなかった仕様側の変数は報告に列挙する | §3 |
| N13 | 文字列 | バイト列として比べる。Unicode 正規化はしない | 範囲外として明記 |

正規化しないと決めたもの: §2.3 の BigNumber 形。D3 で扱いを決める。

## 5. 設計への修正点

### 5.1 中核に明示する仕様（§3 の不足分）

1. 状態 0 を `init` ステップとして扱い、各ステップ後に状態を比べる。ステップ番号は状態の index と一致させる
2. 空の actionTaken は「無名アクション」エラーにする
3. nondetPicks は Option を 1 段外し、`Some` だけを残す。型ごとの取り出し関数を用意する
4. 比較は正準形の値どうしで行い、射影と未比較変数の報告を含める（N12）
5. 実装側の Go 値から ITF 値への変換を中核に置く。アダプタを「対応表のみ」に保つため
6. アダプタの panic を recover し、ステップ単位の失敗として報告する
7. トレースごとにアダプタを新しく生成する
8. トレースはファイル名で整列して処理する
9. 判定はトレース単位で返し、各トレースは最初の不一致で止める

### 5.2 Go パッケージの案（Phase 1 で確定する）

- `itf`: 値の型、トレースのデコード、正準形と等価判定、差分、Go 値からの変換
  - Go 値からの変換規則: タグ付き構造体はレコード、`map[K]V` はマップ、`map[K]struct{}` は集合、slice・配列はリスト、整数型と `*big.Int` は整数、`itf.Value` はそのまま
  - タプルと variant は構築関数で作る
  - ITF 値から Go の構造体へのリフレクションによる復号は、最小構成には入れない。nondet の値は型ごとの取り出し関数で読む
- `mbt`: `Step`（アクション名、picks、期待状態）、アダプタの interface、再生、トレース単位の判定、失敗報告
  - アダプタの interface の案: `Step(Step) error` と `State() (map[string]any, error)`。`init` を含むアクション名から関数への対応表を補助型として用意する
  - 失敗の分類: デコード失敗、無名アクション、未対応アクション、アダプタのエラー、panic、状態取得の失敗、状態の不一致
  - 報告に出すもの: トレースのファイル名、ステップ番号、アクション名、picks、値のパスごとの期待と観測、未比較の変数
- 決定性: 中核とサンプルでは時刻・乱数を使わない。map の走査結果は必ず整列してから使う

行数の見積もりは中核で 800〜950 行。目安の上限（1,000 行）に近いため、超えそうなら Go 値からの変換の対応型を絞る。

## 6. 判断が要る事項

### D1. 差分テストの手段（Phase 2 の前提）

- Rust ツールチェーンが入っていない。差分テストには導入が要る（brew の rustup 1.29.3 か公式インストーラ。版は導入時に固定する）
- quint-connect は与えた ITF を直接読めない。`quint` を PATH から起動して一時ディレクトリに生成させ、最初の失敗で打ち切る。`QUINT_SEED` と `QUINT_VERBOSE` はコンパイル時に読む `option_env!` である
- 案: PATH の先頭に `quint` の代役スクリプトを置き、凍結した ITF を 1 本だけ出力先へ写す。1 回の実行で 1 トレースを判定させ、トレースの数だけ実行する。`QUINT_VERBOSE=1` でビルドすれば、ログの `[Trace n]` と `[Step n]` から不一致のステップ番号を読める
- 忠実な実装どうしでは全件 pass と pass の一致にしかならず、ステップ単位の判定一致を確かめられない。失敗する入力が要る。案: 凍結トレースの一部ステップの状態を決定的に書き換えた改ざんトレースを両方に与え、不一致のステップ番号が揃うかを見る

### D2. 在庫予約モデルの観測可能性（Phase 2・3 の終了条件に直結）

トレースには「有効になったアクション」しか入らない。そのため、モデルの書き方によってはミュータントの種が原理的に検出できない。

- 遷移ガードの欠落（キャンセル済みの確定が通る）: モデルが「キャンセル済みへの確定」を遷移として持たなければ、トレースに出てこない。案: 確定・キャンセルは常に有効にし、結果を `lastResult`（`Ok` / `Rejected(理由)`）として状態に持つ
- `>` と `>=` の取り違え: 予約数がちょうど在庫数に一致するステップが要る。案: 在庫と数量の値域を小さくし、境界に当たる確率を上げる
- 期限切れの扱い漏れ: 案: 論理時刻 `now` と `tick` アクションをモデルに入れ、実装には時計を注入する（決定性を保つため実時刻は使わない）
- 在庫チェックと予約を分離した競合: 1 スレッドの決定的な再生では、同時実行を起こせない。案 A: 予約要求を「受付」と「処理」の 2 ステップに分けてモデル化する。そのうえで複数クライアントの割り込みをトレースで表し、実装の「処理」で在庫を検証させる。これなら決定的に検出できる。案 B: この種を対象外にし、理由を記録する

評価器は Phase 3 で凍結するため、凍結前（Phase 1）に決めておく必要がある。

### D3. Rust バックエンドの整数欠陥（§2.3）への対処

- 案 a: ドライバでは吸収しない。比較でレコードと整数の不一致になったとき、診断メッセージで「Quint Rust バックエンドの 16 桁以上の整数の欠陥の可能性」と示す。サンプルのモデルは 15 桁以下に収める
- 案 b: オプトインの復元機能を設け、明示的に有効にしたときだけ `{s,e,c}` を整数に戻す
- 推奨は案 a。プロンプトの「モデル（.qnt）側の不備はドライバで吸収せず別件として報告する」方針を、Quint 本体の不備にも当てはめた扱いになる
